### 한 일

**공인 IP를 줄일 방법부터 찾았다.** 카카오 챗봇 쪽에서만 공인 IP를 세 개 쥐고 있었다. 한국 리전은 프로젝트당 받을 수 있는 공인 IP 수가 빠듯해서, dev VM 하나를 통째로 줄이는 게 목표였다. 후보를 몇 개 놓고 고르다가 두 가지를 섞기로 했다. 하나는 앱을 도커 이미지(실행에 필요한 걸 통째로 묶은 꾸러미)로 만들어 관리하는 것. 다른 하나는 스테이징(운영에 올리기 전 마지막 시험 무대)을 별도 VM 대신 운영 VM 위 임시 스택(여러 컨테이너를 한 벌로 묶어 띄운 것)으로 올리는 것.

**이미지를 GHCR(깃허브가 주는 이미지 보관소)에서 한 번만 빌드하도록 바꿨다.** 전에는 VM에서 다시 빌드했는데, 이제는 한 번 만든 이미지를 그대로 스테이징 → 운영으로 밀어 올린다. 같은 이미지가 두 단계를 통과하니 "스테이징에선 됐는데 운영에선 안 되네"가 줄어든다. api 이미지를 다루는 운용 헬퍼(자주 쓰는 명령을 모아둔 스크립트)도 같이 넣고, 문서에 깃허브 링크를 달았다.

**스테이징을 운영 VM 위 임시 스택으로 옮겼다.** dev VM을 없애도 검증 단계는 남겨야 하니, 운영 VM 안에서 임시로 띄웠다 내리는 방식으로 만들었다. 배포가 끝나면 Iris(카카오 쪽과 실제로 메시지를 주고받는 다리 역할 서버)까지 왕복으로 찔러보는 검증도 붙였다. 검증에 쓰는 토큰이 운영 설정에 들어가 있는지도 같이 짚었다. 발급한 기억이 없어 되짚어봤는데, 값은 이미 설정돼 있었다.

**Iris 부팅 디스크에 자동 스냅샷 정책을 넣었다.** 테라폼(인프라를 코드로 적어두는 도구)에 정책을 적어서, 디스크가 주기적으로 백업되게 했다.

### 막힌 것, 고친 것

- **왕복 프로브가 영구 404였다.** 배포 후 Iris를 찔러보는 검사가 매번 없는 주소라고 답했다. 원인은 검증용 토큰을 api 컨테이너에 넘겨주지 않은 것. compose(여러 컨테이너를 한 파일로 묶어 띄우는 설정)에서 토큰이 컨테이너까지 가도록 이어줬다.
- **스테이징 배포가 체크아웃에서 죽었다.** 임시 스택을 띄울 때 소스를 받아오는 디렉터리 소유자가 어긋나 있었다. 어느 VM 어느 경로에서 권한을 고쳐야 하는지 짚었고, 이제 CI(코드가 올라오면 검사와 배포를 자동으로 돌리는 장치)가 어긋난 소유권을 스스로 되돌리게 만들었다.
- **비공개 저장소 인증에 걸렸다.** 스테이징에서 쓰는 원격 주소가 운영 쪽과 형태가 달라서 인증이 안 됐다. 주소를 운영 기준으로 맞췄다.
- **사람이 손으로 띄우는 경로가 두 번 막혔다.** 런북(따라 하면 되게 적어둔 작업 순서)대로 가다 DB 이름이 어긋나서 걸렸다. schema.sql에 DB 이름이 박혀 있던 걸 떼어내 특정 이름에 매이지 않게 하고, staging.sh의 수동 경로 세 군데도 같이 손봤다.

### 돌아보며

공인 IP 하나를 줄이자는 얘기로 시작했는데, 끝나고 보니 배포가 도는 방식 자체가 바뀌어 있었다. VM을 하나 없애려면 그 VM이 하던 일을 다른 데로 옮겨야 한다. 옮기다 보니 "왜 여기서 또 빌드하지" 같은 것들이 딸려 나왔다. 자원을 아끼려던 게 구조를 정리하는 일이 됐다.

막힌 것들은 하나같이 사소했다. 토큰을 컨테이너에 안 넘겼고, 디렉터리 주인이 달랐고, DB 이름이 파일에 박혀 있었다. 큰 설계는 한 번에 그려졌는데 정작 발목을 잡은 건 이런 것들이다. 아마 설계는 머릿속에서 끝까지 그려볼 수 있지만, 이런 어긋남은 실제로 돌려봐야만 드러나기 때문일 것이다.

아직 dev VM은 살아 있다. main 배포가 한 번 무사히 도는 걸 보고 나서야 없앤다. 그 순서를 지키는 게 맞다는 걸 안다. 그래도 정리가 눈앞에 있는데 아직 손을 못 대는 상태는 어딘가 근질거린다.
